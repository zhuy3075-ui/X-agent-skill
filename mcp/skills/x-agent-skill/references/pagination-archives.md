# 评论分页与博主档案约定

## 统一身份和存储

三部分使用同一份 PostgreSQL 数据，不在技能目录另建业务 JSON 或每位博主一套数据库表。
档案结构为 `{archive_version:1, author_id, handle, created_at, updated_at}`。
`author_id` 是 X 数字用户 ID，也是唯一键；handle 仅用于查找和展示，不用作去重键。
采集器从已解析的账号身份或根帖作者建立档案，重复操作执行 upsert；身份冲突明确报错。

| 数据 | 存储约定 | MCP 获取方式 |
| --- | --- | --- |
| 博主档案 | `sm_authors`，主键 `author_id` | `query_author_archives(author_id?, handle?, limit?, cursor?)` |
| 帖子归属 | `sm_author_posts`，每个帖子只关联一个博主；保留根帖与回复帖的真实归属 | 由采集器自动写入，不接受 agent 猜测 |
| 操作历史 | `sm_author_operations` 关联 `sm_jobs`；同一博主＋任务唯一 | `query_author_history(author_id, limit?, cursor?)` |
| 帖子 | `sm_posts` 按所属博主关联 | `query_author_data(author_id, category="posts", ...)` |
| 评论 | `sm_comments` 经根帖关联所属博主，评论者另存 | `query_author_data(author_id, category="comments", ...)` |
| 互动记录 | `sm_snapshots` 通过帖子／评论根帖归档，按观测时间追加 | `query_author_data(author_id, category="interactions", ...)` |

查询工具统一返回 `{records, count, has_more, next_cursor}`，每页最多受服务限制（通常 100 条）。
下一页传回不透明 `next_cursor` 并保持筛选条件不变，不用页码或自行生成游标。
操作历史记录任务类型、创建／结束时间、状态、进度及安全错误，不复制 token 或原始认证响应。
查询行为本身不生成采集任务历史。帖子改名、重复采集和任务重试不产生重复档案。

旧数据在 schema 2 初始化时补齐可验证的归属与任务关联，不移动或删除原数据；无法识别根帖作者的
历史评论不随意归档，之后取得根帖身份才能关联。分析时应说明档案覆盖缺口。

## 分页参数传递

1. 博主范围先按档案 ID 枚举帖子；默认只处理本次明确时间窗口中的帖子。
   用户要求整个历史时先采集／核实帖子目录，目录未完整则不能宣称全博主评论完整。
2. 第一批调用 `sync_comments(post_id, request_id, mode="full", scope="thread", max_pages=100,
   max_runtime_seconds=300)`；只要直接回复则用 `scope="direct"`。
3. worker 发出当前 `post_id` 和 `cursor`；首页游标为空。每次成功写页时把新增评论、观测快照、
   当前已访问游标和后续游标队列在同一事务中提交。失败页不能先弹出队列。
4. `Bottom` 和 `ShowMoreThreads` 返回的非空游标进入待处理队列。一次响应有多个分支时全部入队，
   去重后逐个请求；不要只保留最后一个游标。队列中的空首页标记和非空后续游标分别处理。
5. 调用 `jobs_get` 等待本批结束。后端冷却等待由同一任务管理，不重复提交。
   若当前批已结束且 `coverage.pending_branches>0`，调用
   `continue_comments(job_id=<上一批>, request_id=<新的唯一请求标识>, max_pages=..., max_runtime_seconds=...)`。
   工具继承帖子、scope、待处理队列、已访问游标；新批重新获得本批预算，历史数据保留。
   通信重试沿用同一请求标识。一个旧批次已经有续批时，查历史继续最新批次，不建立平行重复链。
6. 整体预算以 config 的 `pagination` 为准。每批使用剩余页数和剩余执行时间的较小值，不能每次
   又分配整份总预算。批数包含失败批；时间从返回的 `progress.active_seconds` 累加，每批只计一次。
   不把冷却等待时间当作正在采集的时间；后端另有最长账号等待时间。

## 结束条件与异常

- **该篇可见范围完成**：待处理队列为空、响应结构已识别、没有未知分页或重复游标导致的缺口，
  覆盖为 `exhausted_visible`。全部目标帖均满足这个条件，且帖子目录范围已核实，才报告本次范围完成。
- 空评论页但仍有后续游标：继续。页内都是重复评论但游标向前推进：继续，数据写入去重。
- 重复游标、未知游标类型、部分响应：保留数据并标记不完整，不能无限循环。
  没有可用游标时 `continue_comments` 返回 `NO_CONTINUATION`；只在用户接受重新扫描时重扫。
- 页数、时长或整体批数耗尽：停止本批或整个流程，保留断点，说明还剩哪些帖子／分页。
  不把预算耗尽写成“没有更多评论”。账号冷却在队列中等待，到达等待上限后给出恢复条件。
- 账号失效／限流：由后端在已配置的有效账号之间切换；不修改帖子和游标，不提高平台配额。
  不同账号可见性和游标兼容性可能不同；无法继续时报告实际错误，不捏造覆盖保证。
- 单帖无权限：记录该帖未完成，继续其他独立目标。用户取消则停止，不自动启动续批。

## 用户可以这样问

- “把他这周发的帖子评论继续翻页采完。” → 复用档案，核实这周帖子范围，逐帖／逐批续采。
- “上次那篇的评论只采了一页，接着采。” → 查历史，继续最新未完成批，不从首页重来。
- “打开这个博主档案，看看之前做过什么。” → 查询档案与操作历史，不访问 X。
- “把这个博主的评论和互动趋势分别给我。” → 按类别查询评论与快照，分别说明范围和观测时间。

只在 agent 本次执行期间编排续批；skill 不是常驻守护进程。后台单个任务可独立运行，
需要跨会话继续时，从档案历史恢复；长期无人值守采集另按明确授权的监测任务配置。
