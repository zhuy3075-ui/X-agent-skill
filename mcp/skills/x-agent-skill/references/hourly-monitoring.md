# 轻量监测约定

## 模块边界与协作

技能理解自然语言、补齐参数并按需解释；MCP 校验参数、建立／暂停任务和查询数据；
worker 独立调度与采集；PostgreSQL 持久保存任务、档案、内容版本、指标快照和变化事件。
MCP 与 worker 同机部署，共用数据库与导出目录；开发时同样可在本机运行。
Agent 不负责每小时唤醒，后台也不调用模型或发送报告。

## 调度与冷启动

新监测首次立即排队建立基线，回补最近 7 天。后续每 3600 秒发现新帖，
同一轮最多核查 5 篇已存、所选帖子类型、默认 30 天窗口内的帖子。
按最久未检查优先轮换，遇到未完成任务不重复排同一帖子。
后台重启后合并错过轮次，不积压补跑每一个小时。未创建监测时没有博主定时采集。
账号有效性检查、队列心跳和失败重试独立于采集周期，不代表每次都抓取博主。

比如 20 篇均需独立核查时，5 篇／小时需要约 4 个小时完成一轮；
新帖可在时间线查询中更早被看到，限流或故障会延迟轮换。
单博主一天正常轮次最多 24 次发现与 120 次帖子查询（假设每轮发现一页）；
多页、重试、账号校验和首次回补另有开销，遵守账号每日配额，不承诺固定耗时。

## 查询接口

- `monitor_upsert(config, request_id, monitoring_requested=true, monitor_id?, expected_version?)`：
  创建／更新监测，返回监测引用、版本、启用状态、下轮时间和预算提示。
- `monitors_list(author_id?, enabled?, limit?, cursor?)`：查询配置、基线水位、最近完成时间和错误。
- `monitor_set_state(monitor_id, enabled, expected_version)`：暂停／恢复后台调度。
- `query_post_changes(author_id, since?, until?, post_id?, limit=50, cursor?)`：
  按观测时间查询；`until` 为排除边界；返回 `records/count/has_more/next_cursor`。
  单条含 `type/post_id/observed_at/payload`。类型为 `new_post/content_changed/availability_changed`；
  编辑含前后正文与内容哈希，状态变化含前后状态、原因，疑似删除的 `deletion_confirmed=false`。
  这是可重复查询的历史，不受 `events_ack` 影响。分页须保留全部筛选条件。
- `query_author_data(author_id, category=posts, limit?, cursor?)`：帖子带当前正文、
  `availability/availability_checked_at/missing_count`，不要把最后一次成功采集时间当作最新状态检查时间。
- `query_metric_snapshots`／`query_growth`：历史指标及实际观测增长；没有两次有效观测则无法得出增长。

## 数据与判断边界

数字博主 ID 和帖子 ID 去重；正文与媒体内容哈希保留版本，指标变动不制造正文版本。
每页数据、状态事件和任务游标在同一租约事务中提交。重复响应和重复提交不制造重复事件。
初次回补不记录为监测期间新增发布；旧帖当前累计指标不能代表过去增长。
失联或无法解析不改变可见性；完整可识别查询缺失记录不可见，至少隔一小时的三次可靠缺失
记录疑似删除。也可能是隐私或账号可见范围变化，不能将其称为已确认删除。
采样可能漏掉两个检查点之间发生又撤回的编辑；窗口以外旧帖不在默认核查范围。

## 用户汇报示例

“从昨天到现在发现 2 条新帖，1 条帖子的正文发生修改。另有 1 条帖子多次查询不到，
可能已删除或改为不可见，目前不能确认。已检查内容覆盖〈范围〉，其余帖子将在后续轮次检查。
互动增长只比较实际保存的快照。”

数字与结论必须来自本次查询；没有历史变化记录可能是未监测、未轮换到或故障，不能直接说没有变化。
